# SFLLVM: a second way to read the compiler (status: used by `sfverify --cross-check llvm`, and by the oracle lane)

**Job (Inspector view):** a second translator. It reads LLVM IR from `swiftc -emit-ir` and encodes it for the same solver, so the SIL reader can be cross-checked against a different view of the same function.
**Raw input → typed → result:** LLVM IR text → `LLVMParser` → `LLVMEncoder` → a verdict from `SFProve`, comparable with the SIL result.
**Depends on:** SFCNF, SFBV, SFProve, SFSIL. **Must not depend on:** SFVerifyKit.
**Fast loop:** `Scripts/sandbox.py SFLLVM` (runs `SFOracleTests`, which start `swiftc` and native binaries: slow, unmeasured). **Connected loop:** `Scripts/sandbox.py SFLLVM --connect`
**Real consumers:** none in production. The only consumer is the oracle lane: `swift test -c release --filter SFOracleTests` (same tests as the fast loop, in release mode), plus the multiplier-hook tests in `SFBVTests`.
**Platforms (verified):** macOS only. It starts `swiftc` with `Process`, and it depends on `SFSIL`, which does not build for iOS.
**Known gaps:** its one consumer is the opt-in `sfverify --cross-check llvm` of the maintainers' scanner (built 2026-11-08, `docs/decisions/0008-sfllvm-status.md`); it reads a smaller part of Swift than the SIL reader, so many proved functions come back `unread` (the reason is in `crossCheckReason`). Since round 6 it follows `-Onone` stack memory byte by byte (`LLVMMemory.swift`), and `LLVMBridge.swift` ties SIL's leaves to the IR's arguments and result through Swift's memory layout (structs in pieces or by reference, `sret`, plain and single-payload enums, `Optional`, tagged multi-payload enums, strings, closures and arrays as handles); results written through an address (`inout`, setters), existentials, multi-payload enums with spare-bit tags, and calls into the standard library stay `unread`. `SoundnessZooTests` (fast) fuzzes the LLVM reader and encoder; the trap on a repeated block label it once found is fixed (`docs/KNOWN-ISSUES.md`, item 3).
