# 0005: API naming against the Swift API Design Guidelines

## Context

Before 0.1.0 every public name was checked against the [Swift API Design Guidelines](https://www.swift.org/documentation/api-design-guidelines/). Most findings were fixed (type names that clashed across tools, `prove` meaning two things, see ADR 0002). The findings below were looked at and left as they are, each for a stated reason.

## Decision

These names stay. A future change needs a new reason, not a new taste.

| Name | Guideline it bends | Why it stays |
|---|---|---|
| `verify_<name>()` generated by `@Verify` | "Everything except types and protocols is lowerCamelCase" | A macro with `prefixed(verify_)` cannot capitalise the next letter. Changing it needs an explicit name at every macro use. Revisit if Swift adds a naming option. |
| `Domain.int(_:)`, `.bool`, `.of(_:)`, `.just(_:)`, `.samples(_:)` | none | They read as a phrase at the call site: `over: .int(0...10)`. |
| `Domain.asSample` | `as…` is for views and conversions | It is a view of the same domain. |
| `Domain.evenlySpaced(_:)`, `.map`, `.filter` | `-ed` and noun forms are for non-mutating methods | They do not mutate. |
| `Counterexample.input: String?` | role-based, but stringly typed | The input is shown to people and replayed from text. Typed replay is a 0.2 idea. |
| `Report.isProved`, `hasNoCounterexample` | none | Boolean properties read as assertions. |
| `Verifier.verify(...)` | none | Reads correctly at the call site. |
| Module prefix `SF…` | short unambiguous prefixes are fine | The engine modules that carry it are not imported by users. |

## Consequences

- Two polish changes were made additively (Phase 6). The old names stay as deprecated forwarding aliases for one minor version and are removed in 0.2:
  - `prove(...)` takes `strategy: ProofStrategy` (`.exact`, `.refiningMultipliers`) instead of a second function name. The `proveRefining` family is `package`. The previous `prove` signature stays as a disfavored overload so that nothing that compiled stops compiling.
  - The capitalised property functions became lowerCamelCase static members of `Property`: `Deterministic()` is now `Property.deterministic()`, `Matches` is `.matches`, `Table` is `.table`, `Injective` is `.injective`, `Image(equals:)` and `Image(within:)` are `.image(equals:)` and `.image(within:)`, `RoundTrip(through:)` is `.roundTrip(through:)`, and `Satisfies` is `.satisfies`. Inside a builder with several properties, write the type (`Property.deterministic()`): Swift reads a line that starts with `.` as a continuation of the previous line. A closure with one property can use `{ .deterministic() }`.
- Later (0.2): the capitalised names came back as **types** that conform to `PropertyConvertible`, so a builder reads
  like SwiftUI (`Prove(it: …) { Deterministic(); Table([...]) }`). Types are UpperCamelCase under the guidelines, so
  this is not the bend the deprecation fixed. `Image` became `Outputs(within:)`/`Outputs(exactly:)`, because SwiftUI
  has an `Image`. The `Property.` factories stay for code that builds a `Property` value.
- Later still (in-place contracts): `import SwiftFormal` became the one import of app files too (it has `@Verify`), and
  an app file imports SwiftUI. So no public top-level name of `SwiftFormal` may be one that SwiftUI, Foundation,
  Combine, Observation or UIKit declares: `Table` became `Matches(table:)` (a table is an oracle written as rows), and
  the deprecated `Table` and `Image` functions moved to `SwiftFormalTesting`, which app files do not import. Names an
  app may also use for its own types (`Report`, `Domain`, `Budget`, `Property`) stay: a type in the app's module
  shadows an imported one, and the code `@Verify` writes names `SwiftFormal.Report` and the like.
- A reviewer who sees one of the names above can point to this page instead of reopening the question.
